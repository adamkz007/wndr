# Finder-Integrated Library Plan

**Date:** May 4, 2026
**Status:** Proposed
**Owner:** Platform Architect / Data & Persistence Engineer

---

## Summary

Look should treat the user-selected library folder as a Finder-visible working library, not only as an app-managed storage root.

This plan changes the storage model so that:

- Imported documents are directly visible in Finder inside the library location.
- Collections are real subfolders inside the library location.
- Tags are written as Finder-compatible macOS file tags.
- Core Data remains the app's metadata index and cache, but no longer acts as the only source of organizational truth.
- App support data moves into a hidden `.look/` directory to avoid cluttering the visible library.

---

## Goals

- Make all imported documents visible and understandable in Finder.
- Make collection membership visible in Finder by representing collections as folders.
- Make tags interoperable with Finder so users can manage tags inside or outside the app.
- Preserve local-first storage and sandbox-safe access through the existing library bookmark flow.
- Keep the app fast by maintaining synced metadata in Core Data.

## Non-Goals

- Multi-folder collection membership for a single document in v1.
- Nested collections in v1.
- Spotlight indexing or cloud sync as part of this change.
- Reworking note-linking, OCR, or search beyond the storage changes required for compatibility.

---

## Current State

Today the library layout is app-managed and mostly optimized for internal storage:

```text
Library Root/
├── PDFs/<doc-uuid>/<filename>.pdf
├── EPUBs/<doc-uuid>/<filename>.epub
├── Notes/<note-uuid>.md
├── Attachments/<attachment-uuid>/<filename>
├── Index/
└── Cache/
```

Current behavior relies on:

- UUID-based document containers generated by `LibraryRootStore`.
- Collection membership stored in Core Data relationships.
- Tag membership stored in Core Data relationships.
- Rename flows that assume the file remains inside a UUID directory.

This works for app-managed storage, but it does not satisfy the requirement that documents, tags, and collections be Finder-visible and Finder-compatible.

---

## Target State

### Visible Layout

```text
Library Location/
├── Inbox/
│   ├── Paper A.pdf
│   └── Book B.epub
├── Literature Review/
│   └── Smith 2024 - Retrieval Systems.pdf
├── Methods/
│   └── Interview Notes.pdf
└── .look/
    ├── Index/
    ├── Cache/
    ├── Notes/
    └── Attachments/
```

### Rules

- Every imported document is stored as a normal visible file.
- Every collection is represented by a real folder directly under the library location.
- Unassigned documents live in `Inbox/`.
- Tags are stored on files using Finder-compatible macOS tags.
- App-private data lives under `.look/`.

---

## Product Decisions

### 1. Collections Are Folders

- A collection maps one-to-one with a folder inside the library location.
- Assigning a document to a collection moves the file into that folder.
- Removing a document from a collection moves it back to `Inbox/`.
- Renaming a collection renames the folder.
- Deleting a collection requires an explicit resolution flow for contained documents.

### 2. One Collection Per Document in v1

- Keep the existing exclusive-assignment model.
- Finder folders naturally express one primary location for a file.
- Avoid aliases or duplicate copies in v1.

### 3. Tags Are Finder Tags

- The app writes document tags as Finder-compatible file tags.
- The app reads Finder tag changes and syncs them back into Core Data.
- Finder-supported color constraints become the product boundary for document tags.
- Core Data tag entities remain for app filtering, counts, and UI performance.

### 4. App Support Data Is Hidden

- Core Data SQLite, caches, thumbnails, notes, and attachments should move under `.look/`.
- The visible library should contain user documents and collection folders, not implementation details.
- `.look/` should be treated as reserved internal app storage.

### 5. Finder Is a First-Class Editing Surface

- Users may rename files in Finder.
- Users may move files between collection folders in Finder.
- Users may add or remove Finder tags in Finder.
- Users may delete files in Finder.

The app must reconcile all of these changes rather than treating them as corruption.

---

## Architecture Changes

### Storage Model

Introduce a storage abstraction that separates:

- Visible document paths
- Hidden support paths
- Logical collection names
- Synced metadata state

This likely belongs in a new service such as `LibraryLayoutService` or a significant expansion of `LibraryRootStore`.

### Core Data Role

Core Data should become:

- Metadata index
- UI query layer
- Cache of synced Finder state
- Relationship store for features that are not file-native

Core Data should no longer be the sole source of truth for:

- Collection placement of documents
- Document tag assignment
- Canonical file location

### Filesystem Sync

Implement a `SyncMonitor` responsible for:

- Discovering new files added directly to the library
- Detecting file moves between collection folders
- Detecting file renames
- Detecting file deletions
- Detecting Finder tag changes
- Reconciling on-disk state with Core Data

Use `NSFileCoordinator` and `NSFilePresenter` around app-initiated file operations to reduce race conditions.

---

## Functional Requirements

### Import

- Import places the file in `Inbox/` by default or into a selected collection folder.
- Import creates or updates the `Document` entity.
- Import applies any chosen tags both in Core Data and as Finder tags.
- Duplicate detection continues to use checksum matching.

### Collection Management

- Create collection: create folder and Core Data record.
- Rename collection: rename folder and update synced paths.
- Delete collection: require user choice for contained files.
- Assign document to collection: move file on disk and update metadata.

### Tag Management

- Create tag in app: create or apply Finder-compatible tag metadata.
- Add tag in app: write Finder tag to the file, then sync Core Data.
- Remove tag in app: remove Finder tag from the file, then sync Core Data.
- Edit tag in Finder: app detects change and updates local metadata.

### External File Changes

- File added to library: import into Core Data without copying.
- File renamed in Finder: update document title or filename mapping according to product rules.
- File moved in Finder: update collection assignment.
- File deleted in Finder: mark missing or remove from library after confirmation/reconciliation.

## Migration Plan

### One-Time Migration

For existing libraries:

1. Ensure the library is backed up or create a rollback manifest.
2. Create `.look/` and move internal support directories into it.
3. Enumerate all existing documents from Core Data.
4. For each document:
5. Determine the current collection assignment.
6. Move the file from `PDFs/<uuid>/...` or `EPUBs/<uuid>/...` into `Inbox/` or the corresponding collection folder.
7. Apply existing app tags as Finder tags.
8. Rewrite stored file paths to the new visible layout.
9. Verify checksums and file existence after migration.

### Rollback Safety

- Record original and destination paths in a manifest.
- Abort on collisions that cannot be resolved safely.
- Provide deterministic filename conflict handling.

---

## Filename and Collision Rules

- Preserve meaningful filenames whenever possible.
- Sanitize filenames for filesystem safety.
- If a destination filename already exists, append a stable suffix such as ` (2)` or an imported date/token.
- Keep internal document UUIDs stable even when filenames change.

The app should not rely on filename uniqueness for identity.

---

## Sync Rules

### App -> Finder

- Collection assignment moves files on disk.
- Tag changes write Finder tags.
- Document rename renames the file.

### Finder -> App

- Moving a file into a collection folder changes collection assignment.
- Renaming a file updates document metadata.
- Finder tag changes update app tag relationships.
- Deleting a file marks the document missing or deleted.

### Conflict Handling

- Coalesce bursts of file events before reconciliation.
- Prefer checksum + path + file attributes over filename-only matching.
- Surface unresolved conflicts in a repair UI instead of silently discarding metadata.

---

## Risks

### Product Risks

- Finder tags support a more constrained model than arbitrary app-defined tag colors.
- Users may expect nested collections once folders become first-class.
- Users may expect notes and attachments to also be Finder-visible.

### Technical Risks

- External edits increase race conditions and sync complexity.
- Sandboxed file coordination must remain reliable across rename and move operations.
- Migration failures could strand files or metadata if not carefully logged and validated.

---

## Open Questions

- Should unassigned documents live in `Inbox/` or directly in the library root?
- Should notes remain hidden in `.look/Notes/` or become Finder-visible too?
- Should Finder filename always be the canonical document title?
- Should collection folders be top-level only, or should nested folders be supported later?
- How should collection deletion behave when the folder contains many documents?

---

## Recommended Rollout

### Phase 1: Internal Refactor

- Introduce visible-vs-hidden library path abstraction.
- Decouple document identity from UUID folder layout assumptions.
- Add support for visible file locations and `Inbox/`.

### Phase 2: Folder-Backed Collections

- Create, rename, delete, and move documents via real collection folders.
- Keep tags app-only during this phase if needed to reduce scope.

### Phase 3: Finder Tag Integration

- Add read/write support for Finder-compatible tags.
- Reconcile app tag color palette with Finder-supported colors.

### Phase 4: Bidirectional Sync

- Add filesystem monitoring and reconciliation.
- Handle rename, move, delete, and direct-library imports.

### Phase 5: Migration and QA

- Run one-time migration for existing libraries.
- Validate Time Machine behavior, sandbox access, and crash recovery.
- Test Finder-driven workflows end to end.

---

## Acceptance Criteria

- Documents imported into Look are visible in Finder within the library location.
- Collections appear as real subfolders of the library location.
- Moving a document between collection folders in Finder updates its collection in Look.
- Applying or removing tags in Look is reflected as Finder-compatible tags on the file.
- Finder tag changes are reflected in Look after sync.
- Existing libraries can migrate without data loss.
- Internal database and cache files are no longer mixed with visible library content.
